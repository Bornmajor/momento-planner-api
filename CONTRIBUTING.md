# Contributing

## Set up

1. **Node.js 24+** and npm.
2. `npm install`, then `cp .env.example .env` and fill it in ([README](README.md#quick-start) explains each value).
3. `npm test`. The first run downloads a MongoDB binary (~800 MB, cached afterwards) for the in-memory test database.
   You don't need Atlas or Docker for tests.
4. `npm run dev` to run the API against your `MONGODB_URI`.

## How work is done

This project follows a documented, spec-first workflow:

1. **Scope** lives in the app repo's `intent.md`, **architecture and API contract** in [spec.md](spec.md),
   **task breakdown** in [plan.md](plan.md). Changing the API contract, data model or stack means updating
   `spec.md` first and agreeing on it.
2. **Tests first:** write the test for the behaviour, see it fail, then implement. Keep tests lean: the main path
   plus the important failure (auth, validation, the key business rule) per feature.
3. **Before every commit**, all of these must pass:
   ```bash
   npm run lint && npm run typecheck && npm test && npm run format:check
   ```
4. **For changes touching Ticketmaster or Claude**, also run the real end-to-end check:
   `npx tsx --env-file=.env scripts/e2e-smoke.ts` (uses real APIs, well under one cent).

## Code conventions

- **Where code goes:** routes handle HTTP only; services hold the rules; providers are the only code that calls
  outside services. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
- **Validate every input** with zod through the `validate` middleware. Don't read `req.body` unvalidated.
- **Errors:** throw `AppError(code, message, details?)` for expected failures. Put internal reasons in
  `{ cause }`, never in `details` (details are sent to clients).
- **Config:** add new env vars to `config/env.ts`, `.env.example` and the README table. Pass values in via
  `createServices`; feature code must not read `process.env`.
- **Imports:** ES modules with `.js` extensions on relative imports (`'./tokens.js'`).
- **Formatting:** Prettier (single quotes, trailing commas, width 110). Run `npm run format`.

## Commits

- Conventional prefixes: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`.
- Mention the plan task when there is one, e.g. `feat(events): T4.4 events routes`.
- No AI co-author or "generated by" trailers.
- **Never commit `.env`** or anything containing keys. Fixtures from real APIs must have keys redacted
  (`scripts/tm-spike.ts` does this).

## Pull requests

Keep PRs focused on one feature or fix. In the description, say what changed and why, how it was tested, and any
`spec.md` change. Reviewers look at the actual diff, not just the summary.
